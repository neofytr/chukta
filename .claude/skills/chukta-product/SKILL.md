# Chukta product guide

## Who it serves

A CA firm's reviewer signs off payment runs for many small-business clients. They care about four things: no wrong payment, no missed deadline, less preparer time, and a file that survives an audit.

Test each feature with: **would this reviewer pay for it, or would it change what they sign?** If neither, skip it.

## The product promise

"Hand over the week's invoices. Get back a payment run you can sign in minutes, with a reason and a source behind every line."

## Rubric, in priority order

| Points | Criterion | What to show |
| - | - | - |
| 25 | End to end | An unseen request becomes a paid run with nobody stepping in except at sign-off |
| 20 | Facts | Each line cites record, field and date. "I can't verify" beats a guess |
| 20 | Robustness | Messy input, a source failure, a kill mid-run, no double payment |
| 20 | Customer value | A paid job, a non-obvious approach, more than a chat box |
| 15 | Demo | Clear story, hardest case, who it could wrong, what comes next |

Ties go to end to end, then facts.

## UI rules

- Lead with the decision the reviewer must make, then the reason, then the evidence.
- Use accounting language: payment run, net payable, TDS, exception, sign off.
- Show rupees in Indian grouping (₹1,18,000).
- Mask bank accounts by default.
- No chat box. The screen is a work queue.

## Who it could wrong

- An honest small vendor unknown to data sources. It gets "I can't verify" and a person, never a fraud label.
- A vendor paid late because Chukta held it. Show the MSME deadline on every hold.

## Demo shape

Open with the request in a customer's words. Run it. Show the fraud catch and its evidence. Kill the process mid-payment and restart. End with one signed run and the audit file. Keep the intro to one sentence.
